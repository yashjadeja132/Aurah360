## Biggest / most user-impacting flow gaps for this role

1. **No consolidated Owner home dashboard.** `/dashboard` is a bare quick-links page with no operational data, no branch switcher, and no attention/alert strip — the doc's entire "90-second morning glance" flow (§1) has no landing screen to support it; the owner would need to already know to go to `/reports` and pick a dashboard card.
2. **No Refunds approval queue and no Pending Approvals (appointments) queue anywhere in the UI.** Both are entire escalation-and-approval steps described as central to the Owner's day-to-day (Billing §9, Appointment §3) but neither has a route, page, or button — the permission constant for refunds exists but nothing consumes it.
3. **Patient 360 is fragmented across modules.** Billing History has zero link from the Patient Profile (must manually re-search in `/billing`), and Appointment History requires a full page navigation to a different route — breaking the "one profile, resolve it without hunting" promise that's the doc's flagship scenario.
4. **Settings/Security/Backup/Audit are missing as Owner-facing screens.** MFA policy management, backup/restore-test evidence, and org-wide audit log browsing — three of the doc's six Settings "stops" — simply don't exist in the frontend; MFA only appears as a personal self-enrollment card on the Profile page, not a governance control surface.
5. **Calendar and conflict-resolution flow is much thinner than described.** The calendar is single-doctor-at-a-time (not a multi-branch/all-doctor week view), filters are plain dropdowns rather than chips, and a booking conflict surfaces only as a generic toast — there is no visual "impacted appointment" banner, no guided reassign/reschedule-with-notification-preview flow, so the doctor-double-booking scenario the doc walks through step-by-step has no matching UI sequence today.

## Biggest user-impacting flow gaps (top 5)

1. **No Branch Manager command-center dashboard (B1).** There is no dedicated Branch Manager landing screen at all — Meera has no equivalent of Kavya's Reception dashboard. She must visit Reception's queue page, Inventory's 3-4 sub-pages, Billing's Cash Close, and a generic Reports hub separately to get the picture the ideal doc assumes is one glance.

2. **Cancel appointment has no mandatory reason (A13).** Both the UI and the backend schema (`cancelAppointmentSchema`) treat `reason` as optional. The ideal flow explicitly requires "Save blocked — reason is mandatory, cannot save a bare cancel." This is a real, verified sequencing/validation gap, not a feature-list nitpick.

3. **Recall "Booked" outcome doesn't hand off into booking (A20).** Recording a recall outcome as `BOOKED` in `RecallWorklistPage.jsx` just saves a status — it does not deep-link into the Book Appointment flow pre-filled with that patient, forcing a second, disconnected search-and-book round trip that the ideal doc explicitly designed away.

4. **Walk-in registration can dead-end with no wait estimate (A10).** `WalkInDialog.jsx` disables Submit entirely when `!slots.length`, with only a text note — no token, no "honest estimated wait," and no alternate-doctor/branch suggestion, unlike the ideal's guaranteed token + wait-estimate outcome for every walk-in attempt.

5. **Invoice discount approval and receipt WhatsApp/Email are non-functional placeholders (A17/A19).** The UI itself calls these out as placeholders (`discountApprovalRequired` is just a flag with no blocking/routing step; `emailPlaceholder`/`whatsappPlaceholder` API calls only mark a flag rather than sending anything) — the ideal flow's hard approval gate and "send receipt digitally as an offline-printer fallback" step are not actually enforced/functional in the current sequence, even though the buttons exist.

## Biggest User-Impacting Flow Gaps

1. **No pre-flight Start Session screen (A3) — safety gate outcomes are invisible.** The backend genuinely enforces consent/patch-test/room/device/credential hard-stops, but the frontend collapses "Begin Procedure" into one button on the same all-purpose session page. When a stop fires, the technician sees only a generic "Start failed" toast — no item-by-item breakdown, no link to who can resolve it, no override affordance despite the backend supporting an audited override. This is the single largest gap between the doc's safety-first design intent and what a technician actually experiences.

2. **Checklist, Parameters, and Consumables are not separate steps — they barely exist as UI at all.** The ideal flow treats these as three distinct, protocol-driven screens with mandatory-step gating, per-area parameter entry, and FEFO-suggested consumable confirmation. In the real app there is one page with four generic free-text fields between Start and Complete; consumables are silently defaulted server-side with zero technician interaction. The entire middle of the technician's clinical workflow — the part the doc treats as most safety/consistency-critical — is functionally missing as a sequenced experience.

3. **Device Status and Room Status don't exist for technicians at all.** Both are backend-enforced gates (good) but have zero dedicated frontend screens for the technician role — the only place device/room config appears is an admin/settings page. A technician's only way to "discover" a blocked room/device is a failed Start attempt, not a proactive glanceable status screen as the doc describes.

4. **Direct Sale is entirely absent.** Not a sequencing difference — the whole B4 flow (walk-in OTC sale) has no frontend route, no backend endpoint, no stock-ledger type. Any walk-in wanting to buy a product without a prescription has no supported path today.

5. **Dispense has no duplicate-medicine warning and "FEFO" is only reliable if the pharmacist leaves the batch field blank.** The doc's B3 flow requires an explicit acknowledgment banner before Confirm Dispense when a duplicate/interacting medicine is detected; that check exists only at prescription-writing time (doctor side), never surfaces on the Dispense screen. Additionally, the batch dropdown auto-fills to whatever batch the API happens to return first when a medicine is selected — true server-side FEFO ordering only kicks in if the pharmacist doesn't touch the batch selector — creating a real risk of the pharmacist believing they've picked a FEFO-correct batch when they haven't.

## Biggest user-impacting flow gaps

- **No approval workflow anywhere in billing.** Discounts apply instantly regardless of size (no reason field, no threshold, no Branch Admin/Owner queue) and cash-close variance reasons aren't actually enforced on submit — this is the single biggest deviation from the PRD's core "mandatory reason + approval threshold" control that both A.5 and A.7 depend on.
- **Refunds and Due Payments are completely missing from the frontend.** There is no refund page/API and no dedicated Due Payments worklist — both are core, everyday cashier tasks (a patient discontinuing a package, or collecting an outstanding balance from a checked-in patient) that today have no UI path at all.
- **No Cashier Dashboard or Cash Opening screen.** Cashiers have no branch-scoped "start of day" experience (drawer status, awaiting-billing worklist, pending approvals) and no distinct drawer-opening event with shift-handover detection — cash opening is folded (informally) into the same form as cash closing.
- **CRM messaging/marketing features (Campaigns, WhatsApp Campaign, SMS Campaign, Reviews, NPS) do not exist in the frontend at all** — only inert "log this channel" placeholder buttons on Lead Detail. This means consent-gating, template enforcement, quiet-hours, and the two-stage review/NPS branching described in the ideal flow have no implementation surface today.
- **Invoice editing lacks the "controlled, price-locked, audited" model.** Cashiers can freely retype item price/discount on any draft invoice with no fee-schedule enforcement and no audit trail beyond a generic timeline entry, and Void only works pre-payment via a bare `window.prompt()` rather than a controlled reason list — increasing risk of silent price overrides and inconsistent audit data.
- **Missed Appointments (CRM) has no dedicated worklist**, even though Follow-up Calls (Recall Worklist) is otherwise the best-implemented CRM screen relative to the ideal spec.

## Biggest user-impacting flow gaps (ranked)

1. **Booking is a flat 3-step picker, not the guided 7-step flow with a Pending-Approval branch.** There's no branch selection, no "continue my follow-up" 1-tap shortcut from a doctor's recommendation, no review/notes step, and — most importantly — no visible Pending-Approval outcome path, so a patient requesting a non-standard time gets the same "Confirmed" alert experience as a normal booking with no way to know their request actually needs clinic sign-off.
2. **Reschedule/Cancel skip all the "why" and "what happens next" messaging.** Both are collapsed into a bare pick-a-slot-then-confirm or a single OS alert — no cutoff-window awareness on reschedule, no reason capture, no package/session-impact transparency, and no post-cancel rebook nudge. A patient rescheduling 30 minutes before an appointment gets the exact same flow as one rescheduling a week out.
3. **No Family-Members add/link flow and no Profile edit capability at all.** The switcher only shows dependents that already exist; a guardian can't add a new one from the app, and neither guardian nor patient can edit any personal detail (name, mobile, emergency contact, consent channel toggles) — Profile is purely read-only plus navigation, cutting out an entire tier of the ideal self-service flow.
4. **Notifications don't deep-link anywhere, and Offers have no booking CTA.** Both are dead-end read surfaces: tapping a notification just flips its read flag instead of opening the related appointment/report, and tapping an offer does nothing at all — removing the "tap-through to act" step the ideal doc treats as the whole point of both screens.
5. **Financial/document screens are shallower and differently organized than modeled.** Receipts don't exist as a screen at all; Invoices open a disclaimed "no real PDF" summary modal instead of an itemized document; and Prescriptions/Reports are merged into one undifferentiated "Documents" list instead of two purpose-built screens with their own status states (Pending Review/Needs Clarification) and detail views.
